# Shared structured data lives only in the French file's frontmatter

Every entity with a page (Zone, Role, Duty, Build core, Build, Gear, Consumable) is one Starlight `docs` MDX entry per locale. Its shared structured fields (template code, references, Loadout, Requirements) live **only** in the French (root-locale) file's frontmatter. The English twin holds just the title, summary and body, and a helper merges the French twin's shared fields into English pages. Translated strings nested inside that data (slot notes, Requirement reasons) are `{ fr, en }` objects. This works because French is the root locale, a CI check guarantees every English page has a French twin, and Sveltia CMS saves non-i18n fields only to the default locale.

## Considered options

- **Gear and Consumables as YAML data with `<StarlightPage>` routes** (the split suggested by the Starlight research): rejected because their prose couldn't use blocks, and those pages would fall outside Starlight's autogenerated sidebar and native fallback.
- **A YAML data entry plus paired MDX prose per entity, joined by slug:** rejected because authors would edit one thing in two places in the editor.

## Consequences

- An English file without a French twin breaks shared data, not just the fallback, so the French-first check is load-bearing.
- Code that reads an entity on an English page must go through the merge helper, never the English entry's own frontmatter.
